# Choosing a search pattern

The <Code>Search</Code> field has three usage patterns. Pick by **what the popup contains**, not by how it looks.

## Search - plain input

No popup. Use it when the field just captures a query and submits it (via <Code>onSearch</Code> or a button). This is the default; reach for it unless you specifically need suggestions.

```tsx
<Search id="q" label="Otsi" onSearch={(query) => runSearch(query)} />
```

---

## Search with suggestions - accessible combobox

Pass a <Code>suggestions</Code> array (even empty) to turn `Search` into a combobox — use it whenever the field should **suggest matches from a dataset** - typeahead, a server-backed lookup, or free-text-plus-suggestions. It implements the [WAI-ARIA combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/): the input is a <Code>combobox</Code> controlling a <Code>listbox</Code> popup. Leave <Code>suggestions</Code> unset for a plain search field.

**Why this and not a Dropdown?** Focus never leaves the input. The arrow keys move a virtual cursor via <Code>aria-activedescendant</Code>, so typing is never interrupted; <Code>Enter</Code> selects the active option (or submits free text via <Code>onSearch</Code>), <Code>Escape</Code> closes the list, and a polite live region announces loading / result count / no-results. A <Code>Dropdown</Code> is a <Code>menu</Code> that moves focus into the list when it opens - which breaks typing - so it is the wrong tool for suggestions.

**You own the data.** Filter or fetch <Code>suggestions</Code> in <Code>onChange</Code> and hand back what should be shown - the component renders exactly that (no internal filtering). Each option is <Code>{'{ value, label?, description?, disabled? }'}</Code>; keep a lookup keyed by <Code>value</Code> on your side for richer payloads. A <Code>description</Code> renders as a second line beneath the label, and the matched substring is bolded automatically; for anything richer use <Code>renderSuggestion</Code>.

```tsx
const [query, setQuery] = useState('');
const suggestions = query ? filter(query) : [];

<Search
  id="people"
  label="Otsi"
  value={query}
  onChange={setQuery}
  suggestions={suggestions}
  onSuggestionSelect={(option) => setQuery(option.label as string)}
/>;
```

## Search + inline results region - result with actions

When suggestions come with fallback actions, prefer the built-in <Code>footer</Code> slot (see the **Autocomplete: with footer actions** story) — it keeps the listbox semantics and manages keyboard focus for you.

Reach for an inline region only when the panel contains things that are **not selectable options at all** - e.g. a single matched result plus action buttons and a hint, with no listbox (a national-registry person lookup is the canonical case) - rendered **below** the field, not in a popup.

**Why not a menu Dropdown?** A floating menu is anchored by <Code>aria-haspopup</Code> / <Code>aria-expanded</Code> on its trigger, and those disclosure attributes are only valid on interactive roles (button, combobox…) - never on a search field or a wrapper div. So anchoring a menu <Code>Dropdown</Code> to a <Code>Search</Code> produces an invalid-ARIA trigger (<Code>aria-expanded</Code> not allowed). And a <Code>combobox</Code> popup may only be a <Code>listbox</Code>, which can't contain buttons. An inline region avoids both: the result and every action are ordinary <Code>Tab</Code> stops - nothing to navigate with disclosure ARIA, nothing to get wrong.

```tsx
<VerticalSpacing size={0.5}>
  <Search id="q" label="Otsi" value={value} onChange={setValue} />
  {hasQuery && (
    <Card>
      <Card.Content>{/* a result button that fills the field, then the action buttons + hint */}</Card.Content>
    </Card>
  )}
</VerticalSpacing>
```

See the **With result and actions** story for the full pattern.
